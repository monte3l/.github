# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The `monte3l` organization's `.github` repository. It has no package manager. It is data GitHub reads directly, the scripts that check and apply it, the tests for those scripts in `tests/`, and the source of the org docs site (monte3l.com), which the vendored m3l-design docs kit builds. Changes here reach other repositories, so think in terms of blast radius:

- **Root community files** (`CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `SECURITY.md`, `SUPPORT.md`) and **`.github/ISSUE_TEMPLATE/` + `.github/pull_request_template.md` + `.github/PULL_REQUEST_TEMPLATE/`** are *live defaults* for every org repo lacking its own copy — a merge here changes them everywhere at once. Wording in these files is written for *other* repositories (e.g. "usually `pnpm verify`"), not this one.
- **`profile/README.md`** is the org's public profile page.
- **`workflow-templates/`** — each `<name>.yml` needs a matching `<name>.properties.json` (name, description, icon, categories) to appear under *Actions → New workflow*. Templates use `$default-branch`, which GitHub substitutes at copy time — keep it, don't hardcode `main`. Already-copied workflows in other repos are *not* updated by edits here.
- **`blueprint/` + `bin/apply-repo-baseline.sh`** — settings GitHub never inherits (rulesets, merge settings, Actions policy, security features, labels), as JSON data, and a script that diffs a repo against them and optionally applies them. `LICENSE`, `CODEOWNERS` and `dependabot.yml` are never inherited either; each repo keeps its own.
- **`design/README.md`** — this repo's marker that it follows m3l-design (vendored tier: `design/source/`, `tokens.css` and `SHA256SUMS` are a verbatim copy, replaced only by `sync-design.sh`; never hand-edit them). `blueprint/design-system.json` pins the release tag (`vX.Y.Z`) every org repo should record; the script only **reports** a missing or stale marker, since adopting is a commit in that repo.

## Docs site

The org site (monte3l.com) is built from this repo by the docs kit in `design/source/docs-kit/` (`docs.config.mjs` is its config). Its home page is `profile/README.md`. Two generators in `bin/site/` render the workflow-template catalog and the baseline-check catalog from `workflow-templates/` and `bin/apply-repo-baseline.sh`, and `bin/doc-parity.mjs` fails the build when documentation and code disagree: the blueprint README's "Repository standard" table against the script's item labels (`bin/lib/baseline-items.mjs` is the one parser), every template against its `.properties.json`, `design-system.json` against `design/README.md`, and `blueprint/projects.json` against the profile README's project table.

- **A new baseline item** is one `report_file`/`report_workflow` line, or an `INLINE_ITEMS` entry in `bin/lib/baseline-items.mjs` if it prints its own OK/DRIFT line, plus a row in the README table with its label in the "Reported as" column. The parity check fails until both exist.
- **A new project** goes in `blueprint/projects.json` (site, card line, description, topics) and in `profile/README.md`'s table, whose row is the description plus a full stop and the site link. `bin/doc-parity.mjs` enforces the wording standard in `blueprint/README.md` under "Descriptions".
- **A new `.md` file** must be added to `pages` or `exclude` (with a reason) in `docs.config.mjs`.
- **The site also publishes for agents.** `docs.config.mjs` sets `llms` and `sitemap`, so the build writes `llms.txt`, `llms-full.txt`, `sitemap.xml` and a `.md` copy of every page. Give a new page a one-line `summary`. A generator returns `summary` and `markdown` for its page, so the copy is a real table and not a link to HTML (`bin/site/*.mjs` do). `--check` fails on a copy with a link it cannot follow.
- **`knowledge/` is an LLM-maintained wiki** (Karpathy's pattern): source cards in `knowledge/raw/` (excluded from the site), interpreting pages in `knowledge/wiki/`, an index, an append-only log, and the schema in `knowledge/CLAUDE.md`, which you read before touching it. `bin/knowledge-parity.mjs` (part of `--check`) enforces frontmatter, existing sources, the index, `pages` entries and log order. A new wiki page needs a `pages` entry with `out` `knowledge/<slug>.html`. The repository is public, so nothing private goes in. Run `/knowledge` to ingest, query or lint.
- The deploy and smoke wiring is `.github/workflows/docs.yml` and `docs-live.yml`, copied from `workflow-templates/`. The Cloudflare setup is `blueprint/docs-site.md`. Pushing to `main` deploys, so the first deploy waits for the `docs-cloudflare` environment to exist.

## Commands

```sh
bin/apply-repo-baseline.sh monte3l/REPO             # read-only, exit 1 on drift, 3 if a call failed
bin/org-audit.sh [--repos a,b]                      # the same over every repo, as one report (read-only); --public prints counts only
bin/apply-repo-baseline.sh monte3l/REPO --dry-run   # also prints the gh api call per drifted item
bin/apply-repo-baseline.sh monte3l/REPO --apply     # mutates the repository — confirm with the user first
node --test "tests/*.test.mjs"                      # the tests: parity gates, the template classifier, and new-repo.sh against stubs (about a minute)
bin/new-repo.sh NAME [--kind K] [--claude] [--private] [--docs] [--scaffold] [--apply [--yes]]   # plan by default; --apply creates a repository and changes org settings — confirm first
```

Needs `gh` (repo admin) and `jq`. Validate edits with `bash -n bin/apply-repo-baseline.sh`, `jq . <file>` on each blueprint JSON, `shellcheck`/`actionlint` if available (not installed by default), `node --test "tests/*.test.mjs"` for the tests, and `node design/source/docs-kit/build.mjs --check` for the site and its parity checks (Node 24, `.node-version`). A change to a script under `bin/` or a parity module needs its case in `tests/`: a test that was only ever run by hand is not a test, and the real runs found bugs (a corrupt lockfile, a branch taken over a tag) that stubs cannot, so a bug found that way gets a test for its cause.

## Blueprint script internals

- This repository is public: `org-audit.yml` publishes counts only (`org-audit.sh --public`), and so does the `copies` job of `freshness.yml` (`template-sync.mjs --public`). The log of `template-sync.yml` has counts only too: in a workflow run (`GITHUB_ACTIONS=true`) `template-sync.mjs --write` prints `refreshed N copies` and `template-sync-pr.sh` how many files and bytes, and their errors name no file, branch, title or `gh` text; by hand they print the full detail. What a public log still shows is the repository name (from the step environment, the token action and checkout), that a leg ran for it, and the URL of the pull request the script prints itself. `tests/sync-log-public.test.mjs` runs both scripts through their failure paths to hold this. Never put per-repository drift, or which copy is behind, in an issue, summary, logs or artifacts: `guard-public-issues.mjs` denies both kinds of line for an org repository name.
- Exit codes: 0 clean, 1 drift in `--check`, 2 usage or a missing tool, 3 any failed call (`trap 'exit 3' ERR`). Keep 1 for drift only: `org-audit.yml` reads 3 as "could not be checked".
- `settle LABEL CURRENT DESIRED METHOD PATH [BODY]` is the single compare-then-act primitive: both sides are `jq -S`-normalized and compared; only on mismatch does it diff/print/apply. `pick` reduces live API JSON to just the keys the blueprint file names — so **a blueprint JSON file owns exactly the keys it lists**; adding a key extends what's enforced, keys not listed are never touched.
- Rulesets are matched to live ones **by `name`** (POST if absent, PUT by id if present) and compared after `normalize_ruleset` (rules sorted by `type`). Renaming a ruleset in a file creates a second ruleset rather than renaming the old one.
- Labels are create-only: an existing label with the same name is never rewritten.
- `PUT /actions/permissions` requires `enabled`/`allowed_actions`, so the SHA-pinning item carries the live values through in its body — follow that pattern for any endpoint whose PUT needs fields the blueprint doesn't own.
- `skip LABEL REASON` prints `SKIP` for items a private repo on a free plan cannot have (fork-PR approval, private vulnerability reporting, rulesets — the latter only on the 403 "Upgrade to GitHub Pro" answer). SKIP is not drift and never sets exit 1.
- `report_file LABEL HINT PATH...` is the report-only primitive for repository files (CODEOWNERS, `.gitleaks.toml`, `.gitattributes`, …): OK if any PATH exists, DRIFT otherwise, never applied. `blueprint/files/` holds the starting points the hints name. A new required file is one `report_file` line plus a row in `blueprint/README.md`'s "Repository standard".
- `report_workflow LABEL HINT PATTERN...` is the same idea for workflow controls: every extended-regex PATTERN must match the concatenated text of the repo's workflows. Use it, not `report_file`, for anything a repository may run from a workflow it already has.
- The `docs site` items apply only to a repository with a `docs.config.mjs` (otherwise one `SKIP`). `docs site: daily check` loops over the workflow files itself, because the schedule and the live check must be in the same file; that is why the first workflow loop also records `workflow_names`.
- `environments.example.json` is deliberately not applied (needs real reviewer ids).
- The `env-janitor:` items apply only to a repository with `.github/environments.json` (otherwise one `SKIP`). `--apply` sets the environment, its `main` policy and removes the repository from an organization secret of the same name: that last one is an **org-level** write (`DELETE orgs/OWNER/actions/secrets/NAME/repositories/ID`), made only once the environment holds the secret. The `JANITOR_APP_*` and `CLOUDFLARE_*` secrets live in the `env-janitor` and `docs-cloudflare` environments (`blueprint/env-secrets.json`), set with `bin/env-secrets.sh set NAME`, never shared from the organization; the `docs-cloudflare:` items apply only to a repository with that environment. Secrets are never created or deleted by the baseline, and extra branch policies are never removed. `janitor_files` mirrors the imports of `m3l-groundwork`'s `bin/cleanup-environments.mjs`: the pin item reports a consumer whose `ref:` predates the newest commit touching them. `settle` and `skip` labels need no README row, but every inline item does (`INLINE_ITEMS`).
- `integration_id` 15368 = GitHub Actions, 57789 = code scanning — global, not org-specific.
- The `main` ruleset requires `verify`, `Dependency Review`, `CodeQL`, `Gitleaks`, `DCO sign-off` and `Commit lint` checks; the `Gitleaks` name must likewise match the job `name:` in `workflow-templates/gitleaks.yml`, and `DCO sign-off` the job `name:` in `workflow-templates/dco.yml` and `Commit lint` the job `name:` in `workflow-templates/commit-lint.yml` (neither may filter by path: a skipped required check never reports); the `Dependency Review` name must match the job `name:` in `workflow-templates/dependency-review.yml`. Likewise `verify` must stay the job `name:` of the aggregator in `workflow-templates/verify.yml`; its `needs` list is the only place lanes are enumerated. Renaming a job in a template silently breaks merges in every repo using the blueprint.

## Conventions

- Every `uses:` in workflow templates is pinned to a full commit SHA with a `# vX` comment (the blueprint enforces SHA pinning, so an unpinned action would fail in adopting repos). `actions/checkout` always gets `persist-credentials: false`. `.github/dependabot.yml` tracks those pins through a second `github-actions` entry with `directory: /workflow-templates` (Dependabot reads a non-root directory directly, one level, `*.yml`; this is source-level behavior, not documented by GitHub). Both entries use a 7-day `cooldown`. If a scheduled run never opens a PR for a stale template pin, the entry doesn't work: fall back to Renovate scoped to that folder. A bump only changes what newly adopting repos copy, but review `claude.yml` bumps closely, and note that `m3l-groundwork` keeps its own copies that these PRs do not touch.
- Workflows start with top-level `permissions: {}` (or `read-all`/`contents: read`) and grant per job; each has `concurrency` and `timeout-minutes`.
- `claude.yml` gates every trigger on `author_association` ∈ OWNER/MEMBER/COLLABORATOR — never relax this; on public repos it is the only thing stopping outsiders from triggering a write-scoped job holding the API secret. `use_commit_signing: true` exists because the `main` ruleset requires signed commits.
- `gitleaks.yml` pins `GITLEAKS_VERSION` by hand — Dependabot doesn't read it. Same for the actionlint image tag and zizmor `version`. `blueprint/pins.json` is the one record of these three (and of the groundwork scaffold version that `bin/new-repo.sh` runs): `bin/pin-parity.mjs` (part of `--check`) fails if a listed file carries another version, and `freshness.yml` opens one `Pinned tool versions are stale` issue weekly when a release at least seven days old is newer. Bump `pins.json` and every file it lists in one PR.
- `blueprint/upstream.json` records the upstream policies (Scorecard checks, OpenSSF Baseline, Best Practices criteria, REUSE spec) as last reviewed by a person. `freshness.yml` opens `Upstream policy changed` when one moves. Update `blueprint/` if the standard should follow, then `bin/upstream-watch.sh --accept NAME` in the same PR. Never accept to silence the report.
- `freshness.yml` runs four weekly jobs, each with its own tracking issue through `bin/lib/upsert-issue.sh`: `pins`, `upstream`, `knowledge` (`bin/knowledge-report.mjs`: a page not reviewed for 180 days, an orphan source card, a dead citation) and `copies` (stale template and starter copies, counts only). A finding never blocks a merge. Never bump a `reviewed` date to clear it.
- **Workflow templates and eleven verbatim starters are rendered per repository and compared by `bin/template-sync.mjs`** (read-only; `freshness.yml` reports a stale copy weekly). `blueprint/sync.json` says which templates and starters are `managed` and where a starter may live (`starters`, `repos.<name>.paths`, and `repos.<name>.twins` for extra verbatim copies of a starter, as `m3l-groundwork` keeps under `templates/core`). `bin/template-sync-pr.sh` sends only a workflow, or a file at a path listed there (a starter's paths, or the repository's own `paths` or `twins`). Never put per-repository data (a URL, an allow-list) in a template: use the `PROJECT` placeholder, a `# sync:if FLAG` block, or a config file. A copy is stale only if it strictly matches an older template version (comments count for that, and only for that), so a change that turns every copy custom makes the sync useless. A difference from the current template in comments, blank lines or pins only makes a copy equivalent: nothing happens. `template-sync.yml` (Mondays 06:15 UTC for real; by hand `dry_run` is on by default) refreshes the stale ones through `bin/template-sync-pr.sh` as the `monte3l-sync` App, one pull request per repository; it never touches a custom copy, and leaves out one whose refresh would rename a job.
- **`blueprint/bootstrap.json` lists what a new repository starts with** (starters, templates, optional parts, where each goes). `bin/bootstrap-parity.mjs` (part of `--check`) fails when a file in `blueprint/files/` or a workflow template is neither listed nor excluded with a reason, so add the entry in the same change as the starter or template.
- **`bestpractices-sync.yml` keeps each registered project's `.bestpractices.json` and its bestpractices.dev answers in step** (`bin/bestpractices-sync.mjs`, rules in `bin/lib/bestpractices.mjs`, the pull request in `bin/bestpractices-sync-pr.sh`). Daily, and a scheduled run is real. A site change becomes a pull request from `monte3l-sync`, a file change becomes a proposal link in the project's `OpenSSF Best Practices sync` issue (the site only saves an answer when a logged-in person clicks Save, and has no token for a job), and a change on both sides is listed and never applied. Which side moved is judged against a hidden `bp-agreed` snapshot in that issue, not a timestamp. A project is found by its repository URL and trusted only when the repository's own README badge names it (anyone can claim a URL on the site, so no badge, or a badge for another id, is an unchecked project); no id is stored here. `--write` refuses a symlink anywhere on the answer file's path, because the checkout comes from the project. Read-only by hand: `node bin/bestpractices-sync.mjs [--repos a,b]`; `--check` exits 1 for a person's turn, 3 for an unchecked project. The run page is public, so it holds counts only (`tests/bestpractices-sync-workflow.test.mjs`, `tests/bestpractices-sync-cli.test.mjs` hold that). It runs in the `bestpractices-sync` environment (listed in `.github/environments.json`, secrets `SYNC_APP_*`) and needs the `monte3l-sync` App to have **issues write** and to be installed on each project. The criteria come from the commit `blueprint/upstream.json` records as reviewed for "OpenSSF Best Practices criteria"; the CLI stops if its scanner and the baseline file disagree on the control count. Never add a request to bestpractices.dev that skips the one-a-second pace. A conflict is never settled by the job: a person decides each one, and `bin/bestpractices-settle.mjs DECISIONS-FILE` (local only, refuses in a workflow) turns the decisions into a Save link per section for `file`, into a file change for `site`, and into both for custom wording (`{ "status", "justification" }`, so the file and the site end up with the same text; custom wording also amends an answer both sides share, because the sync never questions agreement, so an answer wrong on both is a person's check). The decisions file names projects and criteria, so it lives outside every repository, never here. With no snapshot nothing is assumed (see "OpenSSF Best Practices sync" in `blueprint/README.md`): never reintroduce a guess about which side is newer.
- Commits: Conventional Commits, `git commit -s` (DCO sign-off), and signed. Prose style across docs: short, plain sentences explaining **why**, tables for file/option listings, GitHub `> [!WARNING]`-style callouts.
- **Working with Claude Code** (`blueprint/README.md`, "Working conventions"): org policy, not Anthropic guidance. Create and edit skills through `/skill-creator`, and verify a fact against the official source before acting on it, citing the page or saying none exists.
- **Shell** (`blueprint/README.md`, "Working conventions"): read a list into a variable before looping, never `done < <(gh ...)` under the ERR trap, because a failed call then reads as "nothing to do" (`tests/shell-process-substitution.test.mjs` is a ratchet: a script may not gain a site). In the Bash commands you run yourself, the shell is zsh on macOS and an unquoted `$var` is not word-split: use an array, `${=var}`, or write the arguments out. Quote a glob (`--include='*.ts'`) and any URL with a `?`, use `sed -i ''` or the `Edit` tool, and keep each call short: a worktree session refuses a `for` loop, `cd DIR;` or heredoc next to `git`, and a foreground `sleep` is blocked (`gh pr checks N --watch` instead). The table is in "Bash commands that Claude Code runs".
- **m3l-design** is a standing rule for every `monte3l` repo: markdown uses bold (not italics), GitHub alerts matched to severity (max two in a row), plain sentences and tables for tabular data. Copy-based from a published `monte3l/m3l-design` release (`bin/sync-design.sh vX.Y.Z`), never a live dependency. When `blueprint/design-system.json`'s version changes, re-sync `design/` (`sync-design.sh vX.Y.Z <this repo>`) in the same commit (`design-resync.yml` opens that pull request when `m3l-design` publishes a release, and the matching ones in the repositories listed under `consumers`), which also rewrites the version in `design/README.md`; the parity check compares the two. The org standard (content vs vendored tier) is in `blueprint/README.md`'s "Design system" section.
- The blueprint's rationale/checklist lives in `m3l-groundwork`'s `docs/github-blueprint.md`; keep `blueprint/README.md`'s file table in sync when changing blueprint JSON.
